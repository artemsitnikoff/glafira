# v1.7.22 — Дедуп кандидата при импорте hh-отклика (2026-08-30)

Фикс: hh `import_response` плодил дубли — на каждый отклик (negotiation), не найденный
по `hh_negotiation_id`, создавал НОВОГО `Candidate`. Тот же человек с N откликами = N
карточек. Портирован 3-уровневый дедуп по образцу Хабра (`import_habr_response`).

## Что сделано (backend, `services/integrations/hh/service.py`)
- **3-уровневый дедуп кандидата** (когда нет заявки по `nid`):
  1. по `resume_id` — существующий `Candidate` с `external_source='hh'`, `external_id=resume_id`;
  2. по телефону/email — `find_duplicate_candidates` (тот же человек мог прийти из другого источника);
  3. иначе — новый `Candidate` (прежнее поведение).
- **Бережём данные существующего при дедуп-матче** (`reused_via_dedup`): скаляры пишутся
  ТОЛЬКО в пустое; `source`/`external_source`/`external_id` НЕ трогаются (сохраняется
  исходный источник, напр. talantix); секции резюме (опыт/навыки/образование) не трогаются.
- **Одна строка на вакансию** (решение заказчика): если переиспользованный кандидат уже
  имеет заявку на ЭТОЙ вакансии — вторую НЕ создаём и этап/negotiation НЕ трогаем. `nid`
  запоминается в `candidate.extra['hh_seen_nids']`.
- **Поллер** (`poll_responses_now`) добавляет `hh_seen_nids` в `existing_nids` → запомненные
  `nid` пропускаются без дорогого фетча резюме. Строго company-scoped (`extra ? 'hh_seen_nids'`).
- Поведение re-poll (тот же `nid`) и нового человека — без изменений.
- Миграция НЕ требуется (схема не меняется).
